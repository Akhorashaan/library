# Картотека — стек и архитектурные решения

> Домашняя библиотека: добавление книг по ISBN или фото штрих-кода, каталог,
> списки чтения. Self-hosted, PWA (телефон + десктоп).

## Решения верхнего уровня

| Что | Выбор | Почему |
|---|---|---|
| Форм-фактор | PWA, mobile-first | Один код на телефон и десктоп, ставится на домашний экран, работает офлайн. Камера доступна из браузера. |
| Архитектура | Статический SPA + тонкий API | SSR здесь не даёт ничего: нет SEO, нет холодных посетителей, пользователь один. Зато офлайн у полки, куда не добивает wifi, поверх статики получается тривиально, а поверх SSR-фреймворка — отдельной хрупкой конструкцией. |
| Репозиторий | Один `package.json` | Для приложения такого размера монорепо из workspace-пакетов — церемония без выгоды: версии в трёх местах, общие типы через сборку пакета. |
| Данные | SQLite на своём железе | Полный контроль, один файл = весь бэкап, нулевая стоимость. |
| Деплой | Один Docker-контейнер | `docker compose up -d` — тот же процесс отдаёт и статику, и API; БД в volume. |

## Фронтенд

- **React 19.3 + TypeScript 7 + Vite 8** — TS 7 компилируется нативным движком, typecheck идёт секунды.
- **Tailwind CSS 4** — CSS-first конфигурация: токены из `design/tokens.css` переезжают в `@theme` и остаются обычными CSS-переменными. Ретро-детали (зерно бумаги, штампы, разлиновка) — осмысленным CSS, не утилитами.
- **React Router 8** (declarative) — роутинг без фреймворка поверх.
- **TanStack Query 5** — серверное состояние: кэш, инвалидация, оптимистичные апдейты при добавлении книги и перестановке очереди чтения.
- **vite-plugin-pwa 1.3** — service worker, манифест, офлайн-оболочка и кэш обложек.
- **@tanstack/react-virtual** — виртуализация каталога; пара тысяч книг не должна тормозить на телефоне.

### Сканирование штрих-кода

**`barcode-detector` 3.2** (ponyfill поверх `zxing-wasm`).

Даёт единый API `BarcodeDetector` и сам выбирает реализацию: нативную на Android/Chrome, WASM-фолбэк на iOS Safari, где нативного API нет. Один код на оба пути.

Два способа ввода через один детектор:
1. **Живая камера** — `getUserMedia` + покадровое распознавание. Основной сценарий.
2. **Фото из галереи** — `<input type="file" capture>`, детектор по одному кадру. Фолбэк для плохого света, мятой обложки, десктопа без камеры.

**Распознавание целиком клиентское.** Фото не уходит на сервер — туда уезжает уже готовая строка ISBN. Меньше трафика, проще сервер, и снимки домашних полок не копятся в контейнере.

Форматы: EAN-13 (это и есть ISBN-13 на обложке), EAN-8, UPC-A на импорте.

## Бэкенд

- **Fastify 5 на Node 22** — самый обжитой Node-стек: любая проблема уже отвечена, плагины на всё. Выбран сознательно вместо более модного Hono: типизированный клиент из коробки того не стоит, когда взамен теряешь готовые ответы на редкие вопросы. Типы между фронтом и сервером берутся из общих zod-схем.
- **better-sqlite3 13 + Drizzle ORM 0.45** — синхронный SQLite (в однопользовательском доме это плюс: нет пула, нет гонок), типобезопасные запросы, миграции через `drizzle-kit`.
- **Zod 4** — валидация на границе API. Схемы лежат в `shared/` и импортируются обеими сторонами: один источник и для проверки на сервере, и для типов на клиенте.
- Плагины: `@fastify/static` (отдача собранного фронта), `@fastify/cookie` + `@fastify/session` (вход), `@fastify/rate-limit` (на случай, если сервис торчит наружу).

### Почему именно better-sqlite3 — проверено, а не предположено

Встроенный `node:sqlite` выглядел заманчиво: ноль зависимостей, ноль нативной компиляции. **Не подходит — Node собран без FTS5**, `create virtual table … using fts5` падает с `no such module: fts5`. Полнотекстовый поиск здесь центральная функция, а `LIKE '%…%'` по трём тысячам книг — не решение.

Главное возражение против нативного модуля — боль установки — на практике не подтвердилось: `npm install better-sqlite3` ставится за 4 секунды из prebuild, без build tools.

### Поиск

**SQLite FTS5**, токенизатор `unicode61 remove_diacritics 2`. Проверено на кириллице: «толстой» находит «Война и мир», регистр не важен, префикс `шалам*` работает. FTS5-запросы пишутся сырым SQL мимо Drizzle — это нормально и ожидаемо.

### Обложки

Скачиваются один раз при добавлении книги, складываются в `data/covers/`, отдаются статикой. Self-hosted каталог не должен превращаться в решето битых картинок, когда чужой CDN переедет.

### Метаданные по ISBN — каскад

Каскад не «первый ответивший выигрывает», а **сборка записи из двух слоёв**. Это прямо следует из разделения `books` / `copies`: часть полей описывает произведение, часть — конкретное издание, и лучшие источники для них разные.

**Слой произведения** — название, автор, аннотация, жанр, обложка:

1. **LiveLib** (разбор schema.org-разметки, см. ниже) — единственный источник, который стабильно даёт кириллицу в названии, авторе и издательстве, плюс аннотацию и жанр. На контрольной выборке 4/4.
2. **K10plus SRU** — сводный каталог библиотек Германии, сильная славистика. Хранит заглавие и в транслитерации, и в кириллице.

**Слой издания** — год, издательство, страницы, переплёт:

3. **Google Books API** — **свой ключ обязателен**: без него сервис отдаёт `429`, потому что анонимная квота общая на адрес и обычно уже исчерпана кем-то другим. Ключ бесплатный.
4. **OpenLibrary** — свободный, без лимитов. Надёжно даёт число страниц и год конкретного издания.
5. **Library of Congress SRU** — добивка, без ключа.

**Обложки** — `covers.openlibrary.org` по ISBN и картинка из LiveLib, независимо от того, кто дал метаданные.

**Ручной ввод** — финальный фолбэк. Любое поле правится руками: домашняя библиотека всегда содержит то, чего нет ни в одной базе.

Результат кэшируется — повторный скан того же ISBN в сеть не ходит. Замерить покрытие на конкретной коллекции: `scripts/probe-isbn.mjs`.

### LiveLib: что даёт и где врёт

Не API (`api.livelib.ru` отвечает `no such endpoint`), а разбор JSON-LD со страницы. Два запроса: `/find/{isbn}`, затем карточка. `robots.txt` разрешает оба раздела; закрыты списки изданий и страницы пользователей.

Держится на schema.org-разметке, а не на CSS-селекторах. Это принципиально: разметка существует ради поисковой выдачи, поэтому переживает редизайны, от которых обычный парсер умирает. Узел `Book` даёт `name`, `author`, `publisher`, `isbn`, `bookFormat`, `genre`, `datePublished`, `image`, `description`, `aggregateRating`.

**Важное ограничение: LiveLib находит произведение, а не издание.** По ISBN издания 2006 года он отдаёт карточку с `datePublished` 2015 и названием другого издания — потому что группирует все издания в одну книгу, а в разметку кладёт данные какого-то одного из них. Числа страниц (`numberOfPages`) нет вовсе.

Отсюда и разделение на слои: у LiveLib берём то, что не меняется от издания к изданию, а год, страницы и переплёт — у Google Books и OpenLibrary, которые отвечают именно на запрошенный ISBN.

### Почему не магазины и не парсинг

Проверено на живых страницах:

- **ЛитРес торгует электронными изданиями.** Поиск по бумажному ISBN с обложки даёт «ничего не найдено», хотя по названию та же книга находится. У электронной версии свой ISBN либо его нет вовсе.
- **ЛитРес рендерится в браузере.** `__NEXT_DATA__` весит 41 КБ и книг не содержит, `<title>` пустой — curl получает пустую оболочку. Нужен headless-браузер или реверс внутреннего XHR.
- **Магазин знает только то, что продаёт сейчас.** Лабиринт по тому же ISBN издания 2012 года — тоже «ничего не найдено». Домашняя библиотека состоит преимущественно из того, что уже снято с продажи, то есть парсинг откажет именно там, где нужен.
- Читай-город рвёт соединение, Озон редиректит на антибота, Лабиринт отдаёт 333 КБ HTML без единого `ld+json` и `itemprop` — парсинг только по CSS-селекторам, ломается от любого редизайна.

Библиотечные каталоги свободны от всех четырёх проблем: они по своей природе описывают печатные издания, помнят снятое с продажи, отдают машиночитаемый XML и работают по стандарту SRU, который не меняется вместе с вёрсткой.

Парсинг остаётся уместен ровно в одном месте — ручная кнопка «поискать в магазине» на экране ручного ввода, для новинок, которые ещё не дошли до библиотечных каталогов. Отдельным модулем на Playwright, по одному запросу, не в основном потоке. Условия использования магазинов автоматический сбор обычно запрещают; для единичных личных запросов это малосущественно, но строить на этом каскад нельзя.

## Аутентификация

Cookie-сессия, пароль-хеш из переменной окружения. Схема БД с самого начала знает о `user_id`, так что второй читатель в доме добавляется без миграции данных.

## Структура репозитория

```
library/
├─ src/                 React PWA
├─ server/              Fastify + Drizzle + SQLite
│  ├─ db/               схема и идемпотентный DDL с FTS5
│  ├─ metadata/         каскад источников и нормализация
│  ├─ routes.ts         плоский API поверх трёх таблиц
│  └─ seed.ts           наполнение для проверки интерфейса
├─ shared/              zod-схемы и выведенные из них типы — общие для обеих сторон
├─ design/              Дизайн-токены и визуальный прототип
├─ scripts/             пробник источников метаданных
├─ docs/
├─ data/                SQLite-файл и обложки (в .gitignore, в Docker — volume)
├─ vite.config.ts       В деве проксирует /api на Fastify
└─ package.json
```

Один `npm install`, один `npm run dev` (Vite и сервер параллельно). Общие типы — обычные относительные импорты, без сборки промежуточного пакета.

**Миграции.** `drizzle-kit` из зависимостей убран: схема создаётся идемпотентным DDL в `server/db/index.ts`. Причина — FTS5-таблицу и триггеры, которые держат поисковый индекс в согласии с данными, drizzle-kit описывать не умеет, и вести схему в двух местах вредно. Drizzle остаётся как типобезопасный построитель запросов.

## Проверено на живом приложении

- Каскад собирает «Любовь к трем цукербринам» кириллицей от LiveLib, а год `2014` и `446` страниц — от OpenLibrary. LiveLib для этого ISBN отдал бы `2015`, потому что показывает другое издание.
- Кэш: повторный запрос того же ISBN отвечает за 0 мс вместо 13 секунд.
- Поиск FTS5 по кириллице: «цукербрин», «ПЕЛЕВИН», префикс «пелев» и «эксмо» находят нужное.
- Повторный ISBN отбивается `409`, обложка скачивается в `data/covers/`.
- Сквозной путь «ввод ISBN → каскад → карточка в каталоге» проходит за 3,6 секунды.

## Модель данных

- `books` — ISBN, название, автор(ы), издательство, год, страницы, переплёт, жанр, обложка, аннотация, источник метаданных, шифр и ключ сортировки
- `copies` — физический экземпляр: состояние, кому отдан и когда
- `reading` — не начата / читаю / прочитана / брошена, прогресс по страницам, даты, заметка, позиция в очереди
- `unresolved` — стопка «на разбор»: ISBN, которых не опознал ни один источник
- `lookup_cache` — ответы каскада, чтобы повторный скан не ходил в сеть
- `books_fts` — виртуальная FTS5-таблица, синхронизируется триггерами

Разделение `books` / `copies` — потому что дома бывает два издания одной книги, и «кому я её отдал» относится к экземпляру, а не к произведению. Склеить их сейчас — потом больно чинить.

**Чего в модели сознательно нет.** Полка с рядом и оценка книги убраны из приложения. Место на полке требует ручного учёта, который никто не ведёт дольше первой сотни книг, а звёзды дублируют заметку, где сказано больше и своими словами. Вместо координат каталог упорядочен по фамилии автора и разбит буквенными разделителями — искать глазами это помогает не хуже, а поддерживать не требует ничего.

**Ключ сортировки.** Порядок «по автору» — по фамилии, поэтому `sort_key` (фамилия + имя в нижнем регистре) вычисляется при записи и лежит отдельным индексируемым полем. Извлекать последнее слово имени прямо в `ORDER BY` дорого и мимо индекса, а сортировка по строке «Варлам Шаламов» как есть поставила бы его под В.

## Стопка «на разбор»

ISBN, который не опознал ни один источник, раньше просто терялся. Теперь он откладывается в `unresolved`, а каталог показывает напоминание, пока там что-то есть.

**Дубликаты исключены схемой, а не проверками в коде.** Первичный ключ таблицы — сам ISBN, вставка идёт через `ON CONFLICT DO UPDATE`: повторный скан не создаёт строку, а увеличивает `attempts` и обновляет `last_tried`. Счётчик попыток заодно отвечает на вопрос «я это уже пробовал?».

Два места, где состояние держится согласованным само:

- при заведении книги её ISBN удаляется из стопки в том же обработчике, что и вставка, — иначе про это пришлось бы помнить руками;
- отложить ISBN, который уже есть в каталоге, нельзя: маршрут отвечает `409`.

Повторный поиск из стопки идёт с `fresh=1`, мимо кэша. Иначе вернулся бы тот же промах, который туда и записал кэш: неудачи кэшируются наравне с находками, чтобы пять сетевых запросов не повторялись на каждый скан.

## Поиск и фильтры

Поверх FTS5 — фильтры по статусу чтения, «не дома», жанру, автору и издательству, плюс четыре порядка сортировки. Условия собираются в один набор, общий для поиска и обычного просмотра: иначе выдача расходится между режимами, и это замечают не сразу.

Значения фильтров приходят из `/api/stats` со счётчиками. Выбрать фильтр, под который ничего не подойдёт, нельзя — пустые варианты просто не показываются.
